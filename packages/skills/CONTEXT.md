# CONTEXT — packages/skills (Consumer Claude Code Skills)

This document captures domain language, architectural patterns, and key concepts specific to the published skills package.

## Overview

**packages/skills** (`@helvetia-design/skills`) ships Claude Code skills that consuming applications install into their own repo. It is not a design-system runtime package — there are no web components, tokens, or styles here. Consumers run `npx @helvetia-design/skills add`, which copies a skill folder into `<project root>/.claude/skills/`. The project root is the nearest directory above `cwd` (or `cwd` itself) that has a `package.json` and a lockfile (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` or `npm-shrinkwrap.json`). It falls back to `cwd` when none is found.

The first (and currently only) skill is **ds-migrate-from-baloise**: a menu-driven helper for migrating an app from the Baloise Design System (`bal-*`, `@baloise/ds-*`) to the Helvetia Design System (`ds-*`, `@helvetia-design/*`). The menu itself lives in the copied `SKILL.md`; this file documents package conventions, not the menu copy.

## Core Concepts

### Compiled CLI vs. self-contained payload

The package has two parts that must not be confused:

- **Compiled CLI** — `src/cli.ts`, swc-compiled to `dist/cli.js`, exposed as `bin.skills`. Its only job is the `add` subcommand: copy the skill payload into the consumer's `.claude/skills/` directory (creating parents). It copies into a temp folder in `.claude/`, swaps it in with two renames (restoring the old folder if the second fails) and writes `.installed.json` (package version and a SHA-256 per file). A re-run first compares the installed files to that marker and exits 1 listing local changes unless `--force` is passed. Hashing ignores CRLF versus LF. An install without a valid `.installed.json` (missing or invalid) is compared to the new payload once, and the list cannot tell local edits from upstream changes. A leftover `.claude/.ds-migrate-from-baloise.tmp` is deleted at the start, and a leftover `.bak` is restored when no destination exists or deleted when it does. A failed second rename restores the old folder, and if that also fails the CLI throws an `AggregateError` naming the kept backup. Re-running `add` is how a consumer updates the skill. The CLI has no other subcommands until a second skill exists.
- **Self-contained payload** — `skills/ds-migrate-from-baloise/`, plain uncompiled Markdown and dependency-free Node scripts. Copied verbatim. After copy, the skill must run inside the consumer's repo with **zero runtime dependency** back on `@helvetia-design/skills` or this monorepo — no script imports from `node_modules/@helvetia-design/*`.

The compiled CLI is a delivery mechanism. The payload is the product.

### Skill payload, not a plugin

Distribution is `npx @helvetia-design/skills add`. There is no Claude Code plugin manifest and no marketplace registration.

### One `migration.md` per component

**Components** offers three paths. **Manual** lists `components/*.md` and `components/*/migration.md` by the first heading. **Detect** runs `scripts/scan-migratable.mjs` and suggests only used `bal-*` components with a matching `components/<name>/migration.md`. Both dispatch to that migration file, unless the user answers yes to the cascade question. **Scope** takes paths and runs a batch over them. See "Batch: scope and cascade".

### Adding the next component

Paths below are inside `skills/ds-migrate-from-baloise/`.

1. Add `components/<name>/migration.md`. The first heading is the menu title.
2. Write the confirm-then-rewrite steps and the prop mapping in that file. End the Report step with a numbered checklist of every item it reports, as `components/select/migration.md` does. `test/report-contract.spec.ts` checks that Report section and pins the number of attention and coverage items per component, so add an entry for `<name>` to its `expectedCounts` table. When the component needs a finder, add a dependency-free `scripts/scan-bal-<name>.mjs` that prints JSON findings and does not edit files, and invoke it from the migration file.
3. When the legacy component has child tags, add an entry per child to `CHILD_SLUGS` in `scripts/scan-migratable.mjs`. Without it **Detect** reports the child as its own unmigratable component, when the parent migration already covers it.
4. Stop there. **Manual** lists the new file automatically. **Detect** suggests it automatically when the consumer project uses the matching component.

Accordion is the template: `components/accordion/migration.md` (heading `accordion`) and `scripts/scan-bal-accordion.mjs`. It is the richest case — child tags, two legacy shapes, renamed events, removed methods, and props with no replacement. Spinner is the minimal case: one tag, one prop table, nothing lost. The agent rewrites matches after one bulk confirmation. The script does not edit files.

Conventions that hold across every component:

- **The scanner stays flat.** It prints `{ total, files: [{ file, findings: [{ line, snippet }] }] }` and nothing else. The one addition is `unmatched`, present only when a path argument matched no source file. Reach comes from widening the single `USAGE_RE`, not from adding fields — toast matches `balToastController`, accordion matches the four `BalAccordion*` bindings and `BalAccordionBundle`. A scanner's `total` counts matching tags and symbols, closing tags included, because each finding is a line the rewrite must touch. The Detect totals from `scan-migratable.mjs` count usages and skip closing tags, so the two numbers differ for the same component. The first documented exception is checkbox and radio: a finding there may carry an optional boolean flag (`switchGroup`, `unboundControl`, `formsBinding`, `setValue`), present only when true, so an unflagged finding keeps the `{ line, snippet }` shape. The migration file's Scan section says how to act on each flag. The second is modal: its scanner runs three extra regexes (a modal-named ref `open(`/`close(`, `componentProps`, and `present(` on a modal `create` result) only in files that already have a `USAGE_RE` finding. Its output stays flat.
- **Never put a shared event name in a component regex.** `balChange` alone is emitted by 26 legacy components, so it would report checkbox, input, and dropdown usages as findings for whichever component you are migrating.
- **`CHILD_SLUGS` stays explicit.** Never fold by prefix: `bal-input-slider` becomes `ds-slider`, a separate component, not part of the input migration. Before the `CHILD_SLUGS` lookup, Detect strips the suffixes `Service`, `Controller`, `Module`, `CustomEvent`, `Options`, `Props`, `Events` and `Detail` from a `Bal*` name, so `BalModalService` counts for modal and `BalCarouselItemCustomEvent` for carousel.
- **Anything with no `ds-*` equivalent follows one rule per framework.** `SKILL.md` "Unmapped props and handlers" defines it, and each `migration.md` row points to it. See `components/select/migration.md` and `components/popup/migration.md`.
- **Legacy event types, element types and Angular bundles follow one shared rule.** `SKILL.md` "Legacy types and bundles" defines it. A `Bal*CustomEvent`, event alias or `HTMLBal*Element` takes its new type from the tag after the rewrite (`BalInputStepperCustomEvent` on a `ds-counter` becomes `DsCounterCustomEvent`). A detail alias is written out, and `BalProps.*` is left and reported. A `...Bal<X>Bundle` spread becomes the explicit `Ds*` symbols the template uses. It stays while a legacy tag of the bundle is left, and a multi-family bundle such as `BalFormBundle` or `BalComponentBundle` always stays. Each `migration.md` of the twelve scanners listed under Detection names its target types and its bundle and points to that rule. Those twelve scanners list `Bal<X>Bundle`, `BalEvents.Bal<X>*` and the bare `Bal<X>CustomEvent` of their own component, with explicit lookaheads so `BalInputSlider*` does not count for input and `BalDateCalendar*` and `BalDateCell*` do not count for date. Field matches its types only to report them, because `ds-form` and `ds-form-col` are CSS classes without event or element types. A new legacy `Bal<X>*` sibling component, such as `bal-input-slider` next to `bal-input`, needs a negative lookahead in the `BalEvents` branch of the parent scanner, or its types count for the parent.
- **The Report step writes to `ds-migration-report.md`, following `shared/report.md`.** The file sits at the consumer's project root. Init creates it, or whichever step runs first, and every later run appends one section. A line that needs a decision or an action from the consumer goes under "Needs your attention" and into chat. A line that only proves a check ran goes to the file only. Every Report step ends with a numbered checklist, and the step is not done until each number has its own outcome line in the file, found or none found.
- **When the component has methods or events, the migration file carries the sibling-file rule.** Angular splits a component across `x.component.html` and `x.component.ts`, and the class file often calls `present()` or handles an event without ever naming the tag, so the scan cannot see it. The migration file tells the agent to open the same-basename `.ts` beside every `.html` finding. See `components/accordion/migration.md`. The checkbox and radio scans are the one exception. They scan that `.ts` for `setValue()` on a typed group ref. Other methods and listeners there are still not seen.
- **The directory is always the legacy slug**, because Detect derives it from the `bal-*` tag. When the component is renamed, the first heading names both sides so the Manual menu stays readable: `components/app/migration.md` opens with `# app → root`.
- **Fixtures are written inline in the spec** with the local `write()` helper. `test/fixtures/` predates that and serves spinner only; do not extend it.

Done when **Components** lists the new heading and choosing it follows that file.

### Icons travel with the component migration

Every component migration also migrates the icons from `@baloise/ds-icons` and `@baloise/ds-brand-icons` in the files it touches, following `shared/icons.md`. The **Assets** menu item applies the same file to every other file that still uses legacy icons, such as a constants file with no `bal-*` tag, and deletes the legacy config call once no `bal-*` component is left. `SKILL.md` hooks that file into the Scan, Rewrite and Report steps of whichever component file is chosen, so a new component gets icon handling without mentioning it. `shared/` sits outside `components/` so that **Manual** does not list it. `shared/report.md` sits there too. It defines the report file that every Report step writes. `shared/field.md` adds its `F1.`, `F2.`, ... items to the checklist of a form component, `shared/icons.md` adds its `I1.`, `I2.`, ... items after them, the **Assets** step adds the `A1.`, `A2.`, ... items of `shared/fonts-favicons.md` after the `I` items, and `shared/legacy-config.md` adds its `L1.`, `L2.`, ... items last.

- **UI icon** — an icon resolved by name through the design system config (`ds-icon name="…"`, and the `icon` props of other components). A wrong name fails silently at runtime.
- **Brand icon** — an illustration passed as a raw SVG string to `ds-brand-icon` (`svg`) or as a URL (`src`). There is no name lookup. A wrong symbol fails at build time.
- **Icon registration** — handing an icon set to the config at startup. The standard UI icon set is pre-registered, so the legacy registration of the whole set is never carried over. Only a **custom icon**, a registered key that names something other than its own standard icon, is carried over and reported. The legacy registration goes with the whole legacy config call, once no `bal-*` component is left, because every remaining legacy component still looks names up in it.
- **Icon name mapping** — the legacy UI icon names that have no identical counterpart, each mapped to an approximation or reported as lost, plus the names both sets share whose glyph changed meaning, which are kept and reported. It lives in `shared/icon-name-map.json`. A component migration that copies an icon name points at the name rule in `shared/icons.md` rather than keeping its own.

`app` does not copy `icons` onto `ds-root`. The Registration rules in `shared/icons.md` handle it.

`scripts/scan-icon-imports.mjs` takes the component's finding files as extra arguments and scans only those. Without them it scans the whole project, which the Assets step uses and the component report uses to point at files Assets still has to migrate. `test/scan-icon-imports.spec.ts` checks the map against `@helvetia-design/assets`, a workspace devDependency of this package, as `test/css-utils-map.spec.ts` does with `@helvetia-design/styles`.

### Shared extension and skip lists

`scripts/source-scan.mjs` exports `SOURCE_EXTENSIONS` (`.ts .tsx .mts .cts .js .jsx .mjs .cjs .vue .html .htm`) and `SKIPPED_DIRS`. Every script in `scripts/` uses these two lists. `scanSourceFiles` reads `SOURCE_EXTENSIONS` by default. Scripts that need more files extend the list instead of replacing it. `scan-css-utils.mjs` adds `STYLE_EXTENSIONS` (`.css .scss .sass .less`). `detect-baloise.mjs` builds `IMPORT_EXTENSIONS` from it with `.css .scss .sass .json`, and `scan-assets.mjs` and `scan-cleanup.mjs` import that set. The masked text of `MARKUP_EXTENSIONS` (`.html .htm .vue`) follows markup rules. In a `.vue` file, `<script>` blocks follow script rules and `<style>` blocks stylesheet rules, and the template treats only `<!--` as a comment, so text such as `image/*` hides nothing. Every other extension follows script rules. `SKIPPED_DIRS` holds build output, including Nuxt's `.nuxt` and `.output`, because the scanners now read `.js` and `.mjs` bundles. Vue is not a supported target: `detectFramework` knows only Angular, React and HTML, and no `migration.md` describes Vue syntax. The scanners still read `.vue` so that `shared/legacy-config.md` and **Cleanup** see every `bal-*` tag that is left. `SKILL.md` tells component migrations and batches to report `.vue` findings under "Needs your attention" and never to rewrite them. **CSS utils** and **Assets** keep rewriting class strings and icon imports in `.vue` files, as before. `harness/inventory.mjs` keeps its own copy of both lists, aligned by hand, because it must not import from `scripts/`. `test/inventory.spec.ts` fails when the copies drift.

### Batch: scope and cascade

A **batch** migrates every `bal-*` component in a set of files in one run, following `shared/batch.md`. It has two entry points. **Scope** takes paths from the user. The **cascade question** follows Manual and Detect: when the chosen component's files also use other migratable components, the user can migrate them all in one batch.

A batch exists because parents style or query their children by tag across families. `ds-button-group` styles `::slotted(ds-button)` and `ds-checkbox-group` queries `ds-checkbox`. Migrating one family at a time leaves a `ds-*` parent around `bal-*` children, which loses layout or wiring without an error.

- **Scanners accept paths.** Every `scan-bal-*.mjs`, `scan-icon-imports.mjs` and `scan-migratable.mjs` takes files and folders after `<project-root>`. A folder limits the walk to its subtree. The filter lives in `scanSourceFiles` in `scripts/source-scan.mjs`, which returns the paths that matched no source file. A path inside a skipped folder such as `dist` counts as unmatched. With paths, `scan-migratable.mjs` also prints `files`, the component totals per file.
- **Fixed rewrite order.** Structural parents run first (`card`, `modal`, `list`, `accordion`, `tabs`, `steps`, `navbar`, `sheet`, `popup`), `field` and the leaves last (`field`, `button`, `close`, `icon`, `text`, `heading`, `badge`, `tag`, `divider`), everything else alphabetical in between. Sibling rules in a `migration.md` name `bal-*` tags, such as the card rule that wraps a `bal-close` next to the title. Running close first would leave that rule without a match. `shared/batch.md` also says that such a rule matches the `ds-*` form.
- **`field` runs after the form controls.** Each control migration removes the `bal-field` around its own controls via `shared/field.md`. The `field` migration then takes the grid and every `bal-field` that is left.
- **Batch mode is one clause in `SKILL.md`.** Inside a batch a `migration.md` runs only its Rewrite step, still applies `shared/field.md`, and hands back the outcome of its Report items. No `migration.md` mentions batches.
- **Once per batch:** the confirmation, the empty legacy import cleanup, `shared/icons.md`, `shared/legacy-config.md`, and one `<date> batch: ...` section in `ds-migration-report.md` with one coverage checklist per migration.
- **Shared files are reported, not blocked.** A file in the set that is imported from outside it is listed with its importers before the confirmation.
- **No tree resolution.** A batch does not follow imports or Angular selectors into other folders. The user adds those folders to the scope.

When you add a migration, place it in the order list in `shared/batch.md` when it restructures children or is a leaf that other migrations wrap. Otherwise the alphabetical middle group covers it.

### Angular peer check in Init

`detect-baloise.mjs` stops Init before any edit when the app's `@angular/core` major is below the lower bound of the `@angular/core` peer range of `@helvetia-design/angular@<version>`. It reads that range with `npm view` through the injectable `readAngularPeers`. It also stops when it cannot decide, for example when `npm view` fails or a spec has no readable major. `lowestMajor` reads one lower bound (`^`, `~`, `>=`, `=` or a bare version), optionally followed by `<` or `<=` upper bounds, so `>=22.0.0 <24.0.0` gives 22. A `||` range, a hyphen range, `*`, a dist-tag or a protocol such as `workspace:` gives `null`, and Init stops. It compares majors only, uses no semver dependency and does not parse lockfiles. The check runs for npm, pnpm and Yarn.

### Legacy config call stays until the last `bal-*` component

The legacy config call (`initializeBaloiseDesignSystem`, `useBaloiseDesignSystem`, `provideBaloiseDesignSystem`) fills the only config that `bal-*` components read, so no migration deletes it while one `bal-*` component is left. The `app` migration copies its values onto `ds-root` and leaves the call unchanged. `shared/legacy-config.md` is the one place that deletes it: `SKILL.md` runs it at the end of every component migration and in **Assets**, and it deletes the call only when `scan-migratable.mjs` reports no other `bal-*` component.

### Fonts and favicons in Assets

`@helvetia-design/styles/css/design-system` has no `@font-face` rules, so an app renders Arial until it gets a font source. The **Assets** step adds one, following `shared/fonts-favicons.md`. It switches the design-system import to `@helvetia-design/styles/css/design-system.local`, which loads the eight BaloiseCreate `.woff` and `.woff2` files from `/assets/fonts`, and makes the app serve those files there. A project that loads fonts through `@baloise/ds-fonts/scss` gets `@use '@helvetia-design/assets/fonts/scss' with ($font-path: <x>)` instead, through the `./fonts/scss` export of `@helvetia-design/assets`, so the app has one `@font-face` source.

- **Target folder.** The project layout decides, not the framework name. A project with a `public/` folder, a Vite config (`vite.config.{js,mjs,cjs,ts,mts,cts}`) or a Next config (`next.config.{js,mjs,cjs,ts}`) at its root gets the files copied once into `public/assets/fonts`, because Vite and Next serve `public/` even before the folder exists, and the copy creates it. Otherwise, Angular with `src/assets` in the `angular.json` `assets` gets a glob entry with input `node_modules/@helvetia-design/assets/src/fonts`. Plain HTML gets the target folder in the report. The copy script is reported, never written into `package.json`, and uses `node -e` with `fs.cpSync`, so the consumer needs no new dependency.
- **No third-party font host.** The skill never writes `fonts.css` or `fonts.cdn.css` and never keeps an `http(s)` `$font-path`. Those load the fonts from www.baloise.ch or cdn.jsdelivr.net and send visitor IP addresses there, which matters under the Swiss nDSG.
- **Favicons.** `@baloise/ds-favicons/assets/<colour>` paths become `@helvetia-design/assets/src/favicons/<colour>`. The files and the six colours are identical, so tags that point at a copied folder keep their `href`.
- **Init stays out of it.** When Init comments out `css/all`, it reports under "Needs your attention" that the line carried `@font-face` and the app renders Arial until **Assets** runs. It does not insert `design-system.local` itself.
- **`assets` is declared early.** `detect-baloise.mjs` adds `@helvetia-design/assets` to the aliases when the app declares `@baloise/ds-styles`, `@baloise/ds-fonts` or `@baloise/ds-favicons`, because pnpm links only declared packages and the copy source is `node_modules/@helvetia-design/assets`.

The `A` items sit between the `I` items of `shared/icons.md` and the `L` items of `shared/legacy-config.md` in the Assets checklist.

`scripts/scan-assets.mjs` prints `{ total, project: { framework, publicDir, angularAssets }, files }`. `files` keeps the flat `{ file, findings: [{ line, snippet }] }` shape of the component scanners. `project` is the one extra field, because the target folder depends on the project layout, not on any single line: whether `public/` exists or a Vite or Next config sits at the root, and which `angular.json` `assets` entries name `src/assets`, including the arrays under `configurations`. A component scanner never needs that, so it stays flat. `framework` comes from `detectFramework` in `detect-baloise.mjs`. The scanner imports it, `readJson` and `IMPORT_EXTENSIONS` (`SOURCE_EXTENSIONS` plus `.css`, `.scss`, `.sass` and `.json`) from there instead of copying them.

### CSS utils: curated map, raw-text scanner, legacy utilities line

The **CSS utils** menu item rewrites legacy Baloise utility classes in the consumer's markup, following `shared/css-utils.md`, and deletes the Baloise utilities line once no legacy class is left. Component migrations do not rewrite classes. It follows the Assets pattern: a map in `shared/`, a scanner in `scripts/`, a rule file in `shared/`, and a section in `SKILL.md`.

- **Map** — `shared/css-utils-map.json` lists only the classes that differ. Groups: `variants` (`renamed` prefixes such as `widescreen` to `desktop-lg`; `lost` prefixes `widescreen-only` and `high-definition-only`; `unchanged`, every Helvetia prefix the scanner splits off; `identical`, prefixed tokens that keep their name although the prefix is renamed, such as the grid's `widescreen:is-half`; `unsupported`, prefixed tokens whose base exists in Helvetia without that variant, such as `desktop:w-full`), `structure` (`grid`, `col`, `container` to `ds-*`), `structureLost` (modifiers the `ds-*` counterpart lacks: `container` with `is-detail-page` or `is-blog-page` on one element, also across class contexts, is reported as one lost pair), `renamed` (same value), `approximated` (closest class, value changes) and `lost`. The CSS values decide the group, not the name: `radius-normal` and `radius` are both 0.25rem, so it is `renamed`. Spacing aliases such as `mb-small` are identical and not listed. No mapped value is a key.
- **Regenerate** — the diff is generated, the map is curated. `scripts/diff-css-utils.mjs` (package root, not payload) prints `identical`, `baloiseOnly`, `helvetiaOnly` and the suffix, variant, structure and `title` renames it can `propose`. `diffStylesheets` runs `extractClasses` on both sides.

  ```bash
  npm pack @baloise/ds-styles@19 --pack-destination <tmp> && tar -xzf <tmp>/baloise-ds-styles-*.tgz -C <tmp>
  B=<tmp>/package/css; H=../styles/dist/css
  node scripts/diff-css-utils.mjs --baloise $B/utilities/all.css --baloise $B/utilities/grid.css --baloise "$B/core.css#container" \
    --helvetia $H/utilities.css --helvetia $H/design-system.css \
    --classes-out test/fixtures/css-utils/baloise-<version>-classes.txt --modifiers-out test/fixtures/css-utils/baloise-<version>-modifiers.txt
  ```

  The v19 grid lives in `utilities/grid.css` and `.container` in `core.css`, so the generator takes several files; `#container` keeps only the rules of that class. The two fixtures are generated data files, not component fixtures, so they are the one exception to the `test/fixtures/` rule. `test/css-utils-map.spec.ts` reads Helvetia CSS from `@helvetia-design/styles` and fails on every Baloise class the map does not resolve to a Helvetia class or to `lost`, so a new Baloise or Helvetia release shows the exact tokens to sort.

- **Scanner** — `scripts/scan-css-utils.mjs` reads class strings from the raw text, because `source-scan.mjs` masks every string. It reuses the walk, `scanSourceFiles` with `paths`, `endOfString` and the comment-masked text (`source.comments`, the same tokenizer as `masked` without blanking strings). That text keeps JSX text and markup text as written, so a `//` or an apostrophe there is not a comment, and in `.html`, `.htm` and `.vue` only `<!--` is a comment outside `<script>` and `<style>`. JSX detection is tokenizer-light: a `<` opens an element only where an operand is expected, TS generics such as `<T,>` stay code, and an element that never closes, or nests deeper than 128, is read as code again. It rewrites nothing and prints `{ total, files: [{ file, findings: [{ line, snippet, classes: [{ from, to, group }] }] }], dynamic: [...] }`. Class contexts: `class` (quoted or unquoted), static `ngClass`, `routerLinkActive`, `active-class` and `exact-active-class`, `className` and JSX `class={…}` (string, `{'…'}`, static parts of a template literal), `[class]`, `[ngClass]`, `[routerLinkActive]` and Vue `:class`/`v-bind:class`/`:active-class`/`:exact-active-class` (string, array, object with quoted or bare keys), `[class.<name>]`, `@HostBinding('class.<name>')`, `classList.add/remove/toggle/contains`, Angular `host: { class }` and `'[class.<name>]'` keys, and inline `template:` strings. Map lookups use `Map`, so `toString` or `constructor` in a class string maps to nothing.
- **Dynamic** — every place the scan sees but cannot rewrite goes to `dynamic`, never silently away, because a miss would let the step delete the Baloise utilities line while a legacy class is in use. Reasons: `template substitution`, `interpolation` and `string concatenation` (the static parts are still mapped), `non-literal class binding` (a variable, a computed key or a spread in `[ngClass]` or `:class`, or a mapped object key in a `className={cx({ … })}` call), `string literal outside a class context` (a code literal or a literal in a bound attribute such as `:title` or `[attr.class]` that contains a mapped class; `const spacing = 'mt-normal'` holds only an identical class and is not listed), `selector` (`'.grid > .col'`, `'class.grid'`), `class input` (a static `styleClass="…"` or `body-class="…"` on a component, which places the classes itself), `selector in a stylesheet` (a mapped class selector in `.css`, `.scss`, `.sass`, `.less` or a `<style>` block, comments skipped; `@extend` lines may show up but `@extend` itself is out of scope), and `possibly commented` (a class context in a `.tsx`, `.jsx` or `.js` file behind a `//` or inside `/* … */`, which may be JSX text that the scan did not detect as JSX).
- **Legacy utilities line** — after the rewrite a whole-project scan decides. With no class move, no `lost` move and no `dynamic` place left, the step deletes every Baloise utilities line that `detect-baloise.mjs` lists and the utilities TODO comment Init put above it. It keeps the shared TODO of the bundled `css/all` block and never touches the Helvetia utilities line. An uncommented `@baloise/ds-styles/css/all` line is reported, not edited.

### Cleanup: the last step

The **Cleanup** menu item deletes what Init kept for the transition, following `shared/cleanup.md`. It runs last, after every other step, and again once a kept line is gone. `scripts/scan-cleanup.mjs` runs `scan-migratable.mjs` first, with the cleanup extensions, so a `bal-*` tag in a `.vue` or `.js` file counts too. `scan-migratable.mjs` reads masked source, where a tag inside a string literal such as `el.innerHTML = '<bal-tag>'` is blanked, so the cleanup scan also lists every `bal-*` tag it sees only in the comment-masked text as `hidden`. Legacy type namespaces in `types` block too, because removing the dependency breaks their imports. When any of the four lists is not empty, it prints `{ status: 'incomplete', outstanding: { suggested, notYet, types, hidden } }` and the step stops without editing, so a cleanup is never partial.

- **What goes** — every active `@baloise/ds-styles/css/structure` and `css/core` line that is exactly one single-line statement of a shape Init keeps (HTML `<link>`, JS or TS side-effect import or SCSS `@import`/`@use` with one path, `angular.json` styles string). Any other line that names them, such as an `@import` list or a Vite `additionalData` string, is kept as `manual`. Also the Init TODO comment when only such lines sit below it, and every `@baloise/ds-*` dependency that no kept line names. After a deleted dependency the step runs the lockfile's install command.
- **What stays** — a `css/font` or `sass/font` line, `@baloise/ds-fonts`, `@baloise/ds-favicons`, `@baloise/ds-icons` and `@baloise/ds-brand-icons` are left to **Assets**, a `css/utilities/...` line to **CSS utils**, and any other legacy reference, such as `css/all` or `bal-notices.js`, to the consumer. A dependency stays while a kept line in the folder of its `package.json` still names it, or any kept line when no manifest in that line's folder declares the package. A legacy package outside the eight that `detect-baloise.mjs` knows, such as `@baloise/ds-testing`, stays as `manual`. Commented-out legacy lines are reported, never deleted. The scan also reads every `.json`, `.yml` and `.yaml` file except lockfiles, so tsconfig `paths` or a CI step keep a dependency (in YAML only `#` starts a comment), and in `package.json` only keys directly inside a dependency field are skipped, not `overrides` or `resolutions`.
- **Scanner** — it prints `{ status, packageManager, installCommand, remove: { lines, dependencies }, keep: { lines, dependencies }, commented, unreadable }`. `unreadable` lists every `package.json` that is not valid JSON. Lines carry `kind` (`import` or `todo`) or `reason` (`assets`, `css-utils`, `manual` or `legacy-below`). Dependencies carry `packageJsonPath` and `field`, and kept ones `reason` (`used` or `manual`) and `usedBy`. It imports `baloiseDependencies`, `DEPENDENCY_FIELDS`, `detectPackageManager`, `IMPORT_EXTENSIONS`, `installCommand` and `LOCKFILES` from `detect-baloise.mjs` instead of copying them.

The `cleanup` report section has only the `C1.`, `C2.`, ... items of `shared/cleanup.md`.

### Field wrapper travels with the control migration

Every `ds-*` form control renders its own field, so a control inside the legacy `bal-field` > `bal-field-label` + `bal-field-control` + `bal-field-message` wrapper would render two fields. Every form component migration therefore removes the wrapper around the controls it migrates, following `shared/field.md`, in the same pass. `SKILL.md` hooks that file into the Rewrite and Report steps the same way it hooks `shared/icons.md`, so a new form component gets the unwrap without mentioning it.

- **Unwrap** — label text becomes `label`, a danger message becomes `invalidText`, any other message becomes `description`, `bal-field-control` is removed, and `bal-field-hint` becomes a `ds-hint` after the control.
- **Required** — only `required` on `bal-field` or `bal-field-label` counts, and the field level comes first. The unwrap sets `required` explicitly, including `required="false"`. Without a field level, the required default rule in `SKILL.md` decides which controls get an explicit `required="false"`.
- **Angular form binding** — while a control bound with `formControlName`, `[formControl]` or `ngModel` is touched and invalid, `@helvetia-design/angular` sets `invalid` and sets `invalidText` to the first error value when it is a string, otherwise to the error key (`required`, `minlength`). Otherwise it writes `''`. A plain `invalidText` does not survive. `shared/field.md` moves a danger message into a conditional `slot="invalid-text"` child, or sets `autoInvalidOff` for messages built in code, and reports controls with a validator but no message. `SKILL.md` applies that row to every bound Angular control, wrapped or not.
- **Per control** — `ds-segment` has no `color`, and `ds-toggle` has no `color`, `description` or `loading`, and never renders its `label` prop or its documented `helper` slot. A message, `valid` state or `loading` that the target cannot carry is reported as lost. A `bal-field-message` that follows a migrated control outside any `bal-field` gets the same message mapping.
- **Left in place** — a `bal-field` around a control that is still a legacy `bal-*` tag, or around a native element, because neither can take the field props. The `field` migration reports it, and for a legacy control names the component migration to run first.
- **Grid** — `components/field/migration.md` (heading `field → form`) maps `bal-form-grid` to `ds-form` and `bal-form-col` to `ds-form-col`, with the legacy `size` as `desktop:is-N`. It also unwraps every `bal-field` that is left. `CHILD_SLUGS` maps the six child tags to `field`. `bal-form` is a different component and is not matched.

### Steps: panels mode and navigation mode

`ds-steps` runs in panels mode (`ds-step` paired with `ds-step-panel` via `name`/`for`) or navigation mode (each `ds-step` wraps a slotted `<a>`, active step via `aria-current`). The legacy `bal-step-item` was header and content in one element, so `href` decides the mode, and a group mixing both is reported, never rewritten. A group with no content in any item (state-driven steps) gets one empty `ds-step-panel` per item, so `ds-steps` stays in panels mode. Without a panel child it would switch to navigation mode, where steps are not clickable and `dsChange` never fires. A loop of `bal-step-item` is rewritten together with its parent, and a group that cannot be mapped stays `bal-*` entirely. A mixed parent (`ds-steps` with `bal-step-item` children, or without children) is never produced.

### Tabs: panels mode and navigation mode

`ds-tabs` follows the same two modes as steps: `ds-tab` paired with `ds-tab-panel` via `name`/`for` (panels mode), or each `ds-tab` wrapping a slotted `<a>` (navigation mode). The mode is decided by whether any `ds-tab-panel` child exists, so a group with no content in any item (state-driven tabs) gets one empty `ds-tab-panel` per item to stay in panels mode. Loops over `bal-tab-item` are rewritten together with the parent. A group that cannot be mapped stays `bal-*` entirely, including the parent tag, so a mixed parent is never produced.

### Toast and snackbar: hooks inside components, controller outside

In React components and custom hooks, `balToastController` and `balSnackbarController` calls become `useToast()` and `useSnackbar()`. The hooks return `[present, dismiss]`, and `dismiss()` closes only the last notice presented through that hook. Outside components, the migration uses `dsToastController` and `dsSnackbarController` with `defineCustomElement` calls for `ds-alert-container` and the notice element. A `balClose` listener belongs to the component run (toast or snackbar) whose tag it targets. When the target cannot be resolved, the run reports the listener instead of rewriting it.

### Fixed-group versioning

This package publishes as `@helvetia-design/skills`, inside the `@helvetia-design/*` fixed group in `.changeset/config.json`. A changeset bumps it in lockstep with every other package in that group, not on its own version track.

### The skill never commits

The copied skill edits the consumer's files and leaves everything unstaged, including `ds-migration-report.md`. It never runs `git add` or `git commit`. That is the same "leave changes for the user" rule this monorepo uses, applied to a stranger's production codebase.

## Key Constraints

- **CLI surface is `add [--force]` only** — no other arguments, no `list`, no per-skill selection.

A static `bal-step-item` without `href` splits into `ds-step` and `ds-step-panel` (panels mode), and one with `href` becomes a `ds-step` around an `<a>` (navigation mode). Items built in a loop (`.map()`, `*ngFor`, `@for`, `v-for`) are rewritten with their parent into a `ds-step` loop plus a `ds-step-panel` loop, and a step group without content gets one empty panel per step. Mixed groups, `options` groups (whole group, parent tag included), loops that cannot be mapped, panels-mode items without `value` and a dynamic `active` without a `value` stay `bal-*` entirely and are reported. `failed` and `invisible` become `invalid` and `hidden`, `color="primary"` is dropped, and `light-blue`, `debounce` and `prevent` are deleted. `clickable` is deleted, and a non-true value is reported as a behaviour change because steps become clickable. An item's `active` wins over `value`, as in legacy, and moves to `value` on `ds-steps`. `balChange` becomes `dsChange` only on migrated elements, and every `event.detail` read in a same-file handler becomes `event.detail.value`, with the sibling-file rule. `select(step)` becomes a `value` assignment, and the unmapped rule applies to `getOptionByValue()`, `getOptions()`, `setActive()` and `balNavigate`. It reports every loss, then leaves the result unstaged.

Tag: `node <skill>/scripts/scan-bal-tag.mjs <project>` prints the same JSON shape and does not edit files. The tag becomes `ds-tag` (`BalTag` → `DsTag`). The child `bal-tag-group` becomes `ds-tag-group` and is covered by one `CHILD_SLUGS` entry, `tag-group`. The regex also matches `BalTagGroup`, `BalTagBundle` and `balCloseClick`, which only `bal-tag` emits, so it is safe to include. It rejects other `bal-tag-*` names. After one yes, the agent rewrites from `components/tag/migration.md`. Static `size` values move to `sm`, `md` and `lg`. `light` merges into the color for `purple`, `red`, `yellow` and `green` (`purple-light`) and is deleted elsewhere. `color="grey"` and `color="blue"` are deleted, because the `ds-tag` default is what `grey` rendered. `transparent` is deleted. `balCloseClick` becomes `dsCloseClick` with the same `MouseEvent` detail, and the sibling-file rule applies. Dynamic bindings are left in place and reported. The report lists the legacy classes, `data-testid`s, `--bal-tag-*` variables and `aria-disabled` that no longer match, then leaves the result unstaged.

Tabs: `node <skill>/scripts/scan-bal-tabs.mjs <project>` prints the same JSON shape and does not edit files. The tag becomes `ds-tabs` (`BalTabs` → `DsTabs`). The child `bal-tab-item` is part of the migration and is covered by two `CHILD_SLUGS` entries, `tab-item` and `tab-option`, the second because Detect reads `BalTabOption` as a component. The regex also matches `BalTabItem`, `BalTabsBundle` and `BalTabOption`, and rejects `bal-tabs-*` and `bal-tab-item-*`. After one yes, the agent rewrites from `components/tabs/migration.md`. A static `bal-tab-item` without `href` splits into `ds-tab` (label becomes its text) and `ds-tab-panel` (panels mode), and one with `href` becomes a `ds-tab` around an `<a>` (navigation mode). `ds-tab` has no `disabled`, `hidden` or `label`, so groups with a static `disabled` or `invisible` item, `accordion`, `options` (whole group, parent tag included), `handleAsTabList` plus `href`, mixed items, a loop that cannot be mapped, a panels-mode item without `value`, a dynamic label that cannot be rewritten or a dynamic `active` without a `value` are left in place and reported. Looped tabs are rewritten with their parent into a `ds-tab` loop plus a `ds-tab-panel` loop, and a tab group without content gets one empty panel per tab. `optionalTabSelection`, `clickable`, `prevent`, `icon`, `svg`, `bubble`, `subLabel`, `a11yControls` and the layout props are deleted and reported, and `expanded` is never mapped to `fullwidth`. An item's `active` moves to `value` on `ds-tabs` in panels mode and is dropped in navigation mode. `balChange` becomes `dsChange` only on migrated elements, with no emit on programmatic changes. Every `event.detail` read in a same-file handler becomes `event.detail.value`, and the sibling-file rule applies. `select(tab)` becomes a `value` assignment, and the unmapped rule applies to the other legacy methods and to `balNavigate`, `balKeyDown` and the animate events. It reports every loss, then leaves the result unstaged.

Textarea: `node <skill>/scripts/scan-bal-textarea.mjs <project>` prints the same JSON shape and does not edit files. The tag becomes `ds-textarea` (`BalTextarea` → `DsTextarea`). The legacy folder has no child tags, so `CHILD_SLUGS` needs no entry. The regex rejects longer names such as `bal-textarea-*` and `BalTextareaValueAccessor`. It matches `BalEvents.BalTextarea*` and the bare `BalTextareaCustomEvent`, which become `DsTextareaCustomEvent`. After one yes, the agent rewrites from `components/textarea/migration.md`: it adds an explicit `required` false because the default flipped, renames the five `bal*` events to `ds*` only on the migrated element, applies the unmapped rule to `clickable`, drops the `@internal` `setAriaForm()` silently, and reports slot content between the tags, `BalProps.BalTextarea*` types and written-out detail aliases, the `string | null` value change and the new `label`. It leaves the result unstaged.

Detection: `node <skill>/scripts/scan-migratable.mjs <project>` prints used components grouped into `suggested` (migration available) and `notYet` (no migration available), with usage totals, and does not edit files. A total counts opening tags, JSX elements and symbol usages, never closing tags. `types` lists the legacy type namespaces `BalEvents`, `BalProps`, `BalRegion`, `Bal*Language`, `BalConfig*`, `BalBreakpoint*` and `BalPlatform*`, also after suffix stripping (`BalLanguageService`). A namespace member such as `BalEvents.BalSegmentCustomEvent` also counts for its component when that component has a migration. Twelve scanners (button, checkbox, date, field, input, input-slider, input-stepper, number-input, radio, segment, select, textarea) match the `BalEvents.Bal<X>*` members and bare `Bal<X>CustomEvent` names of their component. The migration rewrites them, except field, which reports them. Other component scanners do not match `Bal*CustomEvent` names yet, so such a type keeps its component in `suggested` after the migration until the consumer rewrites it. Types are not components and do not keep the legacy config call, but they block Cleanup. The `bal-popup` attribute counts for popup only inside a tag, so a `.bal-popup` selector or prose does not.
